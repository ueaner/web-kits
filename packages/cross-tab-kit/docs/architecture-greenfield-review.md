# `docs/architecture-greenfield.md` 审查意见

> 审查对象:`docs/architecture-greenfield.md`(绿地架构设计,"应然"视角)
> 审查范围:文档内部一致性、跟 `docs/architecture.md`("实然路径")的一致性、场景到 API 的映射是否
> 真正闭环、导出/命名纪律是否自洽。
> 结论:这是一份扎实的地基文档——场景驱动的 API 排序、`./advanced` 子路径的导出纪律、把测试重心
> 转向并发交错模拟,这三件事在项目刚起步、还没有真实外部消费方之前做,成本最低、收益最高,方向是对
> 的。上一轮对 `architecture.md` 的审查意见(`docs/architecture-review.md`)已经被认真吸收并反映在
> 两份文档里,核对下来两边在核心机制上确实一致。本文档本身发现 4 处问题。

## 1. S1(token 刷新去重)的场景闭环少了关键的最后一句

§2 表格和 §4 的 `tryWithTabLock` 示例只写到"拿不到锁就跳过",但跳过之后调用方该怎么办——它仍然
需要一个可用的 token 才能继续。`architecture.md` 里同样的例子已经把这句补上了:"别的 tab 正在
刷新,本次跳过——通常接着等 storage 事件即可"。

这不是排版遗漏,是场景闭环真正缺的一环:光靠 `tryWithTabLock` 只回答了"谁来刷新",没回答"跳过的
人怎么拿到结果"。既然绿地文档把 S1 列为"极高频"的头号场景,这句收尾应该原样搬过来,不能让两份
并存的文档在同一个场景上出现完整度落差。

## 2. `ctx.signal` 和 `options.signal` 同名但含义不同,容易被读成同一个信号

`withTabLock`/`tryWithTabLock` 的 `options.signal` 中止的是"等锁"这个阶段;`TabLockContext.signal`
(在 operation 内部)中止的是"`timeoutMs` 到期后通知 operation 该收手了"——两个完全不同生命周期、
不同触发条件的 `AbortSignal`,只是恰好都叫 `signal`。调用方很容易以为两者是同一个信号,或者以为
外层传的 signal 会自动传播到 ctx 里。

建议要么在类型/文档里用不同名字区分(比如 `ctx.timeoutSignal`),要么在文档里用一句话把"这是两个
独立信号"讲透,不要只靠读者自己从两处散落的定义拼出来。

## 3. "导出只增不减是 1.0 前的承诺"这句话,方向很可能写反了

§3 末尾这句,读起来是"在到达 1.0 之前,导出只能增加不能减少"——但整份文档的前提是"假设从零开始,
没有 0.1.0、没有兼容包袱",1.0 之前根本没有对外发布过的表面积,谈"只增不减"没有意义;真正该承诺
的应该是"到了 1.0 之后,导出只增不减"(标准的语义化版本承诺:1.0 之前可以自由调整,1.0 之后才开始
认真对待兼容性)。

这处如果按字面执行,会在项目还没到 1.0 时就提前把自己焊死,跟绿地设计本来想要的灵活期正好相反,
建议确认一下是不是笔误。

## 4. `storage-cell` "统一处理……原型污染"这条,承诺可能比这个抽象实际能做到的多

原型污染问题的根源是 `ttl-dedupe` 那种"key 是不受信任的用户输入、可能等于 `__proto__`"的集合型
存储;`poll-lease` 是固定字段的单条记录,压根没有这个风险。如果 `createStorageCell<T>` 只是通用的
"安全读 JSON + 校验 + 安全写"外壳,那么"用 Map 而不是普通对象做中间表示,避免 `Object.fromEntries`
踩坑"这类防护,本质上还是要留在 `ttl-dedupe` 自己手里(它决定怎么把内部 Map 转成要写盘的形状),
`storage-cell` 未必能替它把这件事真正"收编"掉。

这不是设计错了,只是 §5.3 这句话目前说得比实现能兑现的更满,建议真正写代码时把"谁负责防原型污染"
这个边界划清楚,不要让读文档的人以为换了 `storage-cell` 这件事就自动解决了。

## 5. 值得认可、建议保留的判断

- §7 的 `steppable.ts` 思路(把 `claim` 的"读→判断→写"拆成可暂停的三步,精确重演竞态窗口)是个
  聪明的办法,直面了"jsdom 给不了真并发"这个测试上的根本限制,而不是绕开它。
- 用 Chrome intensive throttling 这个真实平台事实取代原来 `max(ttlMs/3, 1000)` 那个拍出来的下限
  (`architecture.md` 已同步这处修正),是修根因而不是打补丁的正确示范。
- 把 `ifAvailable` 从重载改成独立的 `tryWithTabLock` 函数,彻底消灭了上一轮"非字面量调用点静默
  失配"的问题,而且顺便让 API 名字本身就说明了语义(等待 vs 跳过),比原方案更清楚。
- 场景驱动(S1-S8 倒推 API,而不是原语正推)这个方法论本身,是让一个刚起步的库避免"面向内部实现
  细节设计公开 API"这个常见陷阱的正确姿势。

## 6. 与上一轮审查(`docs/architecture-review.md`)的关系

上一轮针对 `architecture.md` 提的 6 条问题里,前 5 条(`onLeadershipLost` 缺字段、`renewIntervalMs`
公式自相矛盾、`pagehide` 承诺过强、`ifAvailable` 重载静默失配、v0.2 一次性加太多面积)都已经在
`architecture.md` 里逐条标注"已修正"并同步反映在这份绿地文档里,核对一致,不再重复列出。唯一没有
直接对应关系的是原来的第 6 条(战略层面的规模判断)——绿地文档用"场景背书 + 15 条按含金量分类"
的方式正面回应了这个顾虑(§6 末尾:"高发条目全部落在 L2 + tryWithTabLock 覆盖范围内——API 面积
有场景背书,无需 @alpha 试水"),这是一个合理的回应,但前提是 S1-S8 这些场景真的来自生产观察而不是
推导——这一点文档本身没法自证,值得在评审时单独确认一次。
